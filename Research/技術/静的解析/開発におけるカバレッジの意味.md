# 開発におけるカバレッジの意味

## 概要

ソフトウェア開発で使われる「カバレッジ（coverage）」の意味を、テストが
コードや要件のどの範囲を実行・確認したものかという観点から調べた。代表的な
指標の違い、数値の読み方、開発チームでの使い方、カバレッジだけでは品質を
保証できない理由を整理する。

## 結論

- カバレッジは、指定した対象（要件、文、行、分岐など）がテストスイートで
  どの程度実行・検証されたかを割合で表す指標である。
- 開発で一般にいうコードカバレッジは、テスト中に実行されたコードの割合を
  指す。行カバレッジが高くても、`if` の真偽や例外などの分岐を十分に確認
  できているとは限らない。
- 行（文）カバレッジは未実行コードを見つける入口として扱い、分岐カバレッジ
  や要件・リスクの観点と組み合わせてテストの不足を判断するのが適切である。
- 100%を目的に機械的にテストを増やすのではなく、重要な振る舞い、異常系、
  境界値、変更箇所をテストし、CIでは新規コードの低下を検知する運用が
  実用的である。
- カバレッジは「テストが存在し、対象が実行された」ことを示すが、アサーション
  が正しいか、期待結果を十分に検証しているか、要件が正しいかまでは示さない。

## 詳細

### 1. カバレッジの基本定義

ISTQBの用語では、カバレッジは「指定されたカバレッジ対象がテストスイートで
実行された程度を百分率で表したもの」と定義される。対象はコードだけでなく、
要件、文、分岐、条件、パスなどにもなり得る。

したがって、カバレッジは単一の数値ではない。何を対象にした割合なのかを
必ず確認する必要がある。たとえば「80%」だけでは、行の80%なのか、分岐の
80%なのか、要件の80%なのか分からない。

### 2. 代表的なコードカバレッジ

#### 行カバレッジ・文カバレッジ

実行可能なソース行または文のうち、テストで一度以上実行されたものの割合で
ある。概念的には次のように表せる。

```text
行カバレッジ = 実行された行数 / 実行可能な行数 × 100
```

```python
if user.is_active:
    allow_login()
else:
    deny_login()
```

`user.is_active` が真のケースだけをテストすると、両方の処理行が実行されない
ため行カバレッジは下がる。ただし、複合条件や短絡評価では、行が実行されても
条件の組み合わせが十分に確認されたとは限らない。

Pythonでは、coverage.pyの通常の測定は文の実行を対象とし、一般的な意味で
行カバレッジとして表示される。JavaのJaCoCoでは、ソース行に対応付けられた
バイトコード命令が一つでも実行されると、その行を実行済みと判定するため、
言語やツールの集計規則を確認する必要がある。

#### 命令カバレッジ

JavaのJaCoCoなどが扱う指標で、コンパイル後のバイトコード命令をどれだけ
実行したかを表す。ソースの改行や書式に左右されにくく、デバッグ情報がなくても
計測できる。一方、開発者が読むソース上の行と直感的に一致しない場合がある。

#### 分岐カバレッジ

`if`、`switch`、ループなどの制御構造で、取り得る分岐先をどれだけ実行したか
を表す。たとえば、真と偽の二つの分岐がある条件で真だけをテストした場合、
その条件の分岐カバレッジは50%になる。

行カバレッジが100%でも分岐カバレッジが100%とは限らない。条件式の行を一度
実行しただけで、片方の分岐しか通っていないケースが典型例である。分岐の
不足は、エラー処理や権限拒否など、通常系以外の振る舞いを見落とす原因になる。

#### 条件カバレッジ

`if (A and B)` のような複合条件で、構成要素の条件A・条件Bそれぞれが真と偽に
評価されたかを測る考え方である。ツールによって「condition coverage」と
「branch coverage」の定義や表示が異なるため、同じ名称でも計算方法を確認する。

#### パスカバレッジ

プログラムの制御フロー上の経路をどれだけ通ったかを表す。分岐が増えると
経路数は急増し、ループがあると理論上の経路が非常に多くなる。そのため、実際の
開発では全パスを網羅するより、重要な経路、境界値、異常系をリスクに基づいて
選ぶことが多い。

#### 関数・メソッド・クラスカバレッジ

関数、メソッド、クラスのうち、少なくとも一部が実行されたものの割合である。
未使用の公開APIや呼び出し忘れを見つける入口にはなるが、関数内部の分岐を
確認したことまでは意味しない。JaCoCoでは、命令が一つ以上実行されたメソッド、
メソッドが一つ以上実行されたクラスを実行済みとして扱う。

### 3. 数値の簡単な読み方

実行可能行が100行あり、テストで75行が実行された場合、行カバレッジは75%で
ある。分岐が40個あり、30個の分岐先を通過した場合、分岐カバレッジは75%で
ある。これらは同じ75%でも、測っている対象が異なるため、単純に同じ品質を
意味しない。

ツールによっては、行と分岐をまとめた「総合カバレッジ」を表示する。しかし、
その算式や分母はツールにより異なる。レポートを比較するときは、対象範囲、
除外設定、テスト種別、集計方式をそろえる必要がある。

### 4. 開発での実用的な使い方

1. **テスト実行時に計測する**  
   単体テストだけか、結合テストやエンドツーエンドテストも含むかを決める。
2. **未実行箇所を調べる**  
   レポートの未カバー行・分岐を読み、仕様上必要なケースか、到達不能コードか、
   意図的に除外したコードかを区別する。
3. **重要な振る舞いにテストを追加する**  
   正常系だけでなく、境界値、入力不正、権限不足、タイムアウト、外部サービス
   障害、例外処理を確認する。
4. **CIで継続的に比較する**  
   カバレッジレポートをビルドで生成し、品質ゲートやプルリクエストで低下を
   検知する。全体値だけでなく、新規コードや変更コードを対象にする方法が
   既存の低カバレッジに埋もれにくい。
5. **計測条件を記録する**  
   テストコマンド、対象ディレクトリ、除外規則、使用ツールとバージョンを
   固定する。SonarQubeのように、外部ツールが生成したレポートを取り込む
   製品もあるため、レポート生成を解析より前に実行する。

### 5. カバレッジの限界と注意点

- **実行は検証ではない**  
  行を通過しただけでは、戻り値、状態変更、ログ、例外、画面表示が正しいかは
  分からない。意味のあるアサーションが必要である。
- **高い数値でもテストが弱いことがある**  
  すべての行を通る一つの大きなテストでも、入力の多様性や境界値を確認できる
  とは限らない。
- **低い数値が直ちに不具合を意味するわけではない**  
  生成コード、単純な委譲、環境依存コードなどは、方針により対象外とすること
  がある。除外理由を残さずに除外すると、数値をよく見せるだけになる。
- **100%を目指す費用対効果は一様ではない**
  重要度の低いコードまで数値のためにテストすると、保守コストが増え、
  仕様の変更を妨げることがある。安全性・金銭・権限・個人情報に関わる部分は、
  全体平均より高い基準を設定するなど、リスクで優先順位を付ける。
- **ツール差がある**  
  コンパイル後の命令を測るかソース行を測るか、例外や短絡評価をどう扱うか、
  除外をどう数えるかがツールごとに異なる。異なる言語やツールの数値をそのまま
  比較しない。

### 6. テストカバレッジとテスト実行結果の違い

テストカバレッジレポートは、テストがコードのどの範囲を実行したかを示す。
一方、テスト実行レポートは、どのテストが実行され、成功・失敗したかを示す。
SonarQubeの公式資料でも、この二つは別の機能として扱われている。カバレッジが
高くてもテストが失敗していれば品質ゲートを通してはならず、逆に全テストが
成功していても重要なコードが未実行なら、テストの不足を調査する必要がある。

### 7. 言語・ツール別の代表的な確認方法

| 対象 | 代表的な確認ポイント |
| --- | --- |
| Python | coverage.pyで通常の文カバレッジを計測し、必要なら`--branch`で分岐も計測する |
| Java | JaCoCoの命令・行・分岐・メソッド・クラス・複雑度を確認する |
| .NET | MicrosoftのコードカバレッジツールやCoverletなどで行・分岐・メソッドを確認する |
| 複数言語・品質基盤 | 各ツールでレポートを作成し、SonarQubeなどへ解析前に取り込む |

具体的なコマンドはプロジェクトのテストランナーやビルド方式に依存する。
まず既存のCIで使っているツールとレポート形式を確認し、別ツールを導入する
場合は除外規則や集計範囲が変わらないか比較する。

C/C++の計測手順とツール選びは、[C・C++のカバレッジ計測方法とツール](./C・C++のカバレッジ計測方法とツール.md)
を参照する。
