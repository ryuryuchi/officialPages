# アプリの静的解析ツールの仕組みと自作方法

## 概要

アプリの静的解析ツールを自作できるか、また既存の静的解析ツールが
実行時に何を調べているのかを確認した。特にPythonで小さな解析ツールを
作る場合を想定し、解析の段階、検出できる問題、実装の難易度を整理する。

## 結論

静的解析ツールは自作できる。最初は、ソースコードを実行せずに構文木
（AST）へ変換し、特定の構文パターンを検査する方式が現実的である。
例えば、未使用インポート、危険な関数呼び出し、複雑すぎる関数、禁止された
書き方を検出し、ファイル名・行番号・修正案を報告できる。

既存ツールが行う処理は、おおむね次の順序である。

1. ソースコードを読み込み、字句解析・構文解析を行う。
2. AST、制御フローグラフ、シンボル情報などの中間表現を作る。
3. ルールに従って構文、名前、制御の流れ、データの流れを調べる。
4. 問題の位置、重要度、説明、修正候補を結果として出力する。
5. CIやエディターと連携し、警告数や品質ゲートで合否を判定する。

ただし、関数をまたぐデータフロー、動的な言語機能、外部ライブラリの挙動、
実行時だけ分かる値まで正確に判断するのは難しい。したがって自作するなら、
まずは「自分のアプリ固有の規約・危険パターンを検出するツール」として
始めるのがよい。

## 詳細

### 静的解析とは

静的解析は、プログラムを実行せずにソースコードや中間表現を調べる方法である。
コンパイル時の誤りを見つけるだけでなく、バグ、セキュリティ上の危険、
保守しにくい書き方、規約違反などを早期に発見する目的で使われる。

「lint」は比較的局所的な文法・スタイル・よくあるミスの検出を指すことが多い。
静的解析はより広い概念で、制御フローやデータフロー、型、呼び出し関係まで
扱う解析も含む。実際の製品では両者の境界が重なることがある。

### 実際の解析パイプライン

#### 1. ソースコードを解析可能な形にする

Pythonなら標準ライブラリの`ast.parse()`で、ソースをASTに変換できる。
ASTは、関数定義、代入、条件分岐、関数呼び出しなどをノードとする木構造である。
`NodeVisitor`などで木を巡回すれば、ソースコードを実行せずに構造を調べられる。

例えば、次のようなルールを作れる。

- `eval()`や`exec()`を呼び出している
- `subprocess`を危険な引数で呼び出している
- 関数の行数やネストが設定値を超えている
- `except Exception`を広く捕捉している
- 秘密情報らしい文字列をソースに直接書いている

#### 2. 名前と型を解決する

ASTだけでは、`run()`という呼び出しがどの関数を指すか分からない場合がある。
そこで、定義された関数・クラス・変数・インポートを記録するシンボルテーブルを
作り、参照先を解決する。型注釈や型推論も加えると、存在しない属性アクセスや
不適切な引数の検出に近づける。

#### 3. 制御フローを調べる

条件分岐、ループ、例外処理、早期リターンなどをグラフとして表すと、
到達しないコード、常に同じ結果になる条件、初期化前の利用、複雑な分岐を
調べられる。関数内だけの解析は比較的実装しやすいが、関数間・モジュール間に
広げるほど呼び出し先の解決が難しくなる。

#### 4. データフローと汚染追跡を行う

データフロー解析は、値がどこから来て、どこへ渡る可能性があるかを追跡する。
セキュリティ解析では、外部入力を「汚染された値」として、SQL実行、
HTML出力、OSコマンド実行などの「危険な到達先」まで追跡する。

例えば、HTTPパラメーターが文字列連結を経由してSQL実行関数へ渡る経路を
警告できる。一方、サニタイズ関数や別名参照、動的ディスパッチを正確に
扱うには、より高度なモデルが必要である。

CodeQLの説明では、ASTが構文構造を表すのに対して、データフローグラフは
実行時に値を運ぶ意味上の要素と辺を表すと整理されている。また、関数内だけを
見るローカル解析は速く、関数間やオブジェクトのプロパティまで見るグローバル
解析は計算コストが高い。

### 自作するならどう作るか

#### 小さく始める構成

Pythonなら、次の構成でMVPを作れる。

1. `pathlib`で対象ファイルを列挙する。
2. `ast.parse()`で各ファイルを解析する。
3. `ast.NodeVisitor`を継承したルールごとの検査クラスを実装する。
4. `Finding(rule_id, path, line, column, message, severity)`のような結果を集める。
5. テキスト、JSON、SARIFのいずれかで出力する。
6. 終了コードを、問題なしは`0`、検出ありは`1`にしてCIから利用する。

最初に向いているルールは、対象プロジェクトの規約に直結するもの、例えば
「GUIスレッドから直接重い処理を呼ばない」「特定のAPIには必ずタイムアウトを
指定する」「本番コードで`print`を使わない」である。汎用的な何百種類もの
ルールを最初から再実装するより、誤検知を抑えやすい。

#### 実装例の考え方

`eval()`検出なら、ASTの`Call`ノードを訪問し、呼び出し対象が名前`eval`かを
確認するだけでよい。行番号はノードの`lineno`から取得できる。
一方、「ユーザー入力がSQL実行まで届いたか」の検査では、入力元、変数への代入、
関数呼び出しによる受け渡し、サニタイズ、危険な実行先を追跡する必要がある。
この差が、単純なパターンルールと本格的な静的解析エンジンの難易度差である。

### 既存ツールとの違い

| 種類 | 主な対象 | 特徴 |
| --- | --- | --- |
| Ruffなどのリンター | 文法、規約、よくあるミス | 高速で、ルール単位の導入と自動修正に向く |
| Semgrep | パターン、関数内データフロー、汚染追跡 | 独自ルールを作りやすく、速度と柔軟性を重視 |
| CodeQL | プログラム全体の意味、データフロー | データベース化したコードをクエリで調べる。高度だが重い |
| Clang Static Analyzer | C/C++/Objective-Cのバグ | シンボリック実行やパスを考慮した解析を行う |
| SonarQube | 品質、バグ、セキュリティ、保守性 | 複数言語、履歴、品質ゲート、CI連携をまとめて扱う |

Semgrepの公式説明では、ASTを解析向けの中間言語へ変換して分析する一方、
主に関数内の解析で、全経路の厳密な実現可能性や複雑な別名関係までは保証しない。
これは静的解析が「すべてのバグを証明するもの」ではなく、速度、精度、対応言語、
誤検知・見逃しのトレードオフを持つことを示している。

### できることとできないこと

静的解析で得意なのは、次のような「コードから推測しやすい問題」である。

- 禁止API、危険API、規約違反の検出
- 未使用インポート、未定義名、到達不能コードの検出
- 複雑度、重複、関数サイズなどの指標化
- 入力値から危険な処理へのデータフローの候補検出
- PRごとの差分チェックと品質ゲート

反対に、次の判断は静的解析だけでは確定しにくい。

- 実際のユーザー操作や本番データでだけ起こる不具合
- 外部サービスの応答や設定値に依存する動作
- リフレクション、`eval`、動的インポートなどで実行時に決まる呼び出し
- 「この仕様がユーザーの期待に合うか」という業務上の正しさ

そのため、静的解析はテスト、型チェック、依存関係スキャン、実行時監視と
組み合わせて使う。警告を増やすことより、重要なルールを選び、誤検知を減らし、
CIで継続的に確認できる状態にすることが重要である。
