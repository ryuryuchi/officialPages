# ループエンジニアリング

## 概要

AIコーディングで最近使われ始めた「ループエンジニアリング」について、
用語の意味、Ralph Loopやハーネスエンジニアリングとの関係、具体的な設計要素、
向いている用途、導入時の注意点を一次情報中心に整理する。

## 結論

- ループエンジニアリングは、人がAIへ一手ずつプロンプトを送る代わりに、
  **仕事の発見、割り当て、実行、検証、記録、次の行動、停止までを反復する仕組み**
  を設計する考え方である。
- Addy Osmaniが2026年6月に「人間のプロンプト役をシステムで置き換える」と
  定義して広めた新しい呼称である。ただし、反復型エージェント自体は以前からあり、
  Geoffrey HuntleyのRalph Loop、ReAct系のエージェントループ、長時間エージェントの
  ハーネス設計などを包括する上位の運用設計と捉えるのが妥当である。
- 成否を分けるのは、プロンプトの巧さよりも、**機械的に判定できる完了条件、
  外部テスト、状態の永続化、1回ごとの小さな作業単位、権限制御、反復回数や
  コストの上限**である。
- AI自身の「できました」を完了判定にしてはいけない。テスト、ビルド、静的解析、
  ブラウザ操作、別エージェント、人によるレビューなど、成果物の外側に検証器を置く。
- 現時点では確立した標準規格ではなく、製品機能や実務パターンをまとめた新しい
  用語である。単純作業へ一律に適用するより、反復可能で客観的に検証できるタスクへ
  段階的に導入するのがよい。

## 詳細

### 用語の意味と成立

Addy OsmaniはLoop Engineeringを、概ね「エージェントへプロンプトを送る人間自身を
置き換え、その仕事をするシステムを設計すること」と定義している。ここでいう
ループは、目的を与えられたAIが完了まで反復する再帰的なゴールである。

従来の対話型AIコーディングでは、次の順序を人が繰り返す。

1. 人が状況を読む。
2. 人が次のプロンプトを書く。
3. AIがコードを変更する。
4. 人が結果を確認し、次の指示を考える。

ループエンジニアリングでは、このうち定型化できる部分をシステムへ移す。

1. 課題、CI失敗、依存更新などから仕事を見つける。
2. 優先順位を付け、作業エージェントへ渡す。
3. エージェントが計画、実装、テストを行う。
4. 外部の検証器が完了条件を判定する。
5. 未達なら失敗内容を次の反復へ渡す。
6. 達成なら記録して停止し、必要に応じて人へレビューを依頼する。

2026年8月時点で「Loop Engineering」は新しい実務用語であり、学術的に統一された
定義や標準規格ではない。Osmaniの記事は考え方を明文化して普及させた主要な
一次情報だが、反復型エージェント全般の最初の発明を主張するものではない。

### Ralph Loopとの関係

Geoffrey Huntleyが広めたRalph Loopは、同じゴールやプロンプトを繰り返し与え、
エージェントに1ループ1タスクで前進させる単純なオーケストレーションパターンで
ある。Huntley自身も、エンジニアの役割を個々のコード作成からループのプログラムへ
移すと説明している。

両者の関係は次のように整理できる。

| 用語 | 主な対象 | 特徴 |
|---|---|---|
| プロンプトエンジニアリング | 1回の指示 | AIへ何をどう依頼するかを改善する |
| コンテキストエンジニアリング | 1回または1セッションの入力 | 必要な規則、コード、履歴を適切に見せる |
| ハーネスエンジニアリング | 1体のエージェントの実行環境 | ツール、権限、状態、テスト、制約を整える |
| Ralph Loop | 単純な反復実行 | 同じ目標を繰り返し、1回に1タスクずつ進める |
| ループエンジニアリング | 反復する業務システム全体 | 発見、分配、実行、検証、記憶、停止を設計する |

したがって、Ralph Loopはループエンジニアリングを実装する最小パターンの一つと
考えられる。Loop EngineeringはRalphの単純反復に加え、スケジュール実行、
並列作業、役割分離、外部連携、永続メモリ、監視、コスト管理まで扱う。

### 主要な設計要素

Osmaniは五つの機能と、一つの外部記憶を挙げている。

1. **Automations**
   - 定期実行やイベントを起点に、仕事の発見と仕分けを行う。
2. **Worktrees**
   - 並列エージェントごとにGit worktreeなどで作業場所を分離し、変更の衝突を防ぐ。
3. **Skills**
   - プロジェクト固有の手順や知識をファイル化し、毎回推測させない。
4. **Plugins and connectors**
   - Issue、CI、ブラウザ、データベースなど、既存ツールと接続する。
5. **Sub-agents**
   - 実装役と検証役を分け、作成者自身による甘い自己評価を減らす。
6. **External memory**
   - Markdown、JSON、Issue、プロジェクトボード、Git履歴などへ、完了済みと
     次の作業を会話の外に保存する。

これらすべてを最初から導入する必要はない。最小構成は「明確なゴール、
作業エージェント、外部テスト、進捗ファイル、反復上限」でよい。

### 実用的な最小ループ

最初に試すなら、次の流れが安全で分かりやすい。

1. **仕様をテスト可能な項目へ分解する**
   - 例: 「ログインを改善する」ではなく、「無効なパスワードで401を返す」
     「有効な認証情報でセッションを作る」のようにする。
2. **完了条件を固定する**
   - 対象テスト、ビルド、型チェック、lintが成功する。
   - 要件一覧がすべて合格になる。
   - 変更範囲外のファイルを触っていない。
3. **1ループ1項目に制限する**
   - 未完了項目を一つ選び、実装、検証、記録まで終えてから次へ進む。
4. **状態を外部へ保存する**
   - 要件ごとの合否、実施内容、残課題、既知の失敗をJSONやIssueへ残す。
   - Gitコミットを回復地点として使う。
5. **外部検証を実行する**
   - AIの説明ではなく、実際のテスト結果や画面操作で合否を決める。
6. **失敗を次の入力へ変換する**
   - エラーログと未達要件を次の反復へ渡し、再計画させる。
7. **停止またはエスカレーションする**
   - 合格時は停止する。
   - 最大反復回数、時間、費用、同一失敗回数の上限に達したら人へ戻す。

Anthropicの長時間コーディング実験では、最初のエージェントが全機能を
`feature_list.json`へ分解し、後続エージェントが毎回一機能だけ進め、
`claude-progress.txt`とGit履歴へ引き継ぎを残す構成が有効だった。単に高レベルの
指示を繰り返すだけでは、一度に多くを実装して途中でコンテキストを失う、
未完成なのに完了宣言する、エンドツーエンドで動かない、といった失敗が起きた。

### 向いているタスク

- 失敗したテストやCIを直し、再実行で合否を確認できる作業
- 依存関係更新、警告除去、定型的な移行など、小単位へ分解できる保守
- 多数の明確な受け入れ条件を順番に実装する長時間タスク
- Issueの分類、重複確認、ドキュメント同期などの定期処理
- 実装とレビューを分離できる複数エージェントのワークフロー

### 向いていないタスク

- 1回で終わる短い修正や、反復の準備コストの方が大きい作業
- 「使いやすく」「格好よく」など、完了条件を客観化できない依頼
- 仕様や優先順位について、関係者の合意形成が必要な作業
- 本番削除、本番デプロイ、課金、秘密情報の操作など、誤動作の影響が大きい処理
- 十分なテストや観測手段がなく、誤った変更を検知できないコードベース

### 主な失敗パターンと対策

| 失敗 | 原因 | 対策 |
|---|---|---|
| 無限反復と費用増加 | 停止条件や上限がない | 回数、時間、トークン、費用の上限を設ける |
| 未完成で完了宣言 | AIの自己評価に依存 | 外部テストと固定した要件一覧で判定する |
| 同じ失敗の繰り返し | エラーと試行履歴を保存していない | 失敗分類、試行済み対策、エスカレーション条件を記録する |
| スコープの拡大 | ゴールと変更範囲が曖昧 | 1ループ1項目、変更可能範囲、禁止事項を固定する |
| コンテキスト劣化 | 全履歴を詰め込み続ける | 新しいコンテキストと短い外部引き継ぎを使う |
| 検証の形骸化 | 実装役が自分で合格判定する | 別エージェント、CI、テスト、人のゲートを使う |
| 並列作業の衝突 | 同じ作業ツリーを共有する | worktree、ブランチ、ファイル所有範囲を分ける |
| 危険な自律実行 | 権限が広すぎる | サンドボックス、許可リスト、最小権限、人の承認を使う |

### セキュリティと運用上の注意

Anthropicの公式デモは、OSレベルのサンドボックス、プロジェクトディレクトリ外への
ファイル操作制限、実行コマンドの許可リストを重ねている。これは、長時間かつ
自動で回すほど、通常の対話セッションより防御を強くする必要があることを示す。

特に次はループの外側に残すべきである。

- 本番環境への反映や不可逆な削除の最終承認
- 秘密情報、個人情報、決済情報へのアクセス
- セキュリティ例外の承認
- 法務、規制、組織方針に関する最終判断

GitHub Agentic Workflowsのような製品機能も登場しているが、2026年8月31日時点でも
Public Previewである。ワークフローはMarkdownから`.lock.yml`へコンパイルし、
GitHub ActionsまたはGitHub CLIと`gh-aw`拡張で実行する。新しいコマンドや
自動化機能を組織の標準として安定していると決めつけず、仕様変更、利用料金、
監査ログ、権限範囲を確認して導入する。

### 実務での判断基準

次の質問にすべて答えられるタスクは、ループ化しやすい。

- 何をもって完了とするか。
- 合否を誰または何が判定するか。
- 1回で処理する最小単位は何か。
- 次の反復へ何を保存するか。
- 何回、何分、いくらまで実行するか。
- どの失敗で停止して人へ戻すか。
- AIに許可する操作と禁止する操作は何か。

答えられない項目がある場合は、先に要件、テスト、権限、監視を整える方が、
モデルやプロンプトを変更するより効果が高い。

### 現在の環境で実現できる範囲

2026年8月31日に、このワークスペースで再確認した環境は次のとおりである。

- Windows上のVS Code 1.135.0
- GitHub Copilot CLI 1.0.68
- Git 2.53.0
- Copilot Agent HostのAutopilotセッション
- サブエージェント、テスト実行、Problems診断、ブラウザ操作、GitHub操作、
  セッション内のTodoデータベースを利用できる
- ルートの`AGENTS.md`と`.github/copilot-instructions.md`から
  `Rule/Rule.md`を参照するプロジェクト指示がある
- GitHubリモートへコミットとpushができる
- GitHub CLI、Claude Code CLI、Codex CLIはコマンドとして未導入
- ワークスペース固有の`.vscode`設定はない

**結論として、この環境だけでも人が開始する半自動のループエンジニアリングは
実行できる。** 現在の調査作業自体が、次のループをすでに構成している。

1. `Rule/Rule.md`から完了条件と作業手順を読み込む。
2. 既存メモを調査し、重複や不足情報を判定する。
3. 必要に応じてサブエージェントとWeb検索へ作業を分ける。
4. 調査結果をMarkdownへ保存する。
5. Problems診断、差分チェック、保存ファイルの再読で検証する。
6. 不備があれば修正し、合格後にコミットしてpushする。

コーディング用リポジトリでも、プロジェクトに既存のテスト、ビルド、lint、
型チェックがあれば、同じCopilot環境で「実装、検証、修正」のループを回せる。
Git worktreeもGit本体で利用できるため、複数エージェントの作業場所を分離できる。
Copilot CLI以外の専用CLIは必須ではない。

一方、現状のままでは次の意味で**完全自動の常時ループではない**。

- ユーザーの依頼またはセッション開始が起点で、定期実行やIssueイベントによる
  自動起動は設定されていない。
- セッション内Todoは利用できるが、別セッションをまたぐ汎用的な要件台帳としては
  Git管理されたJSON、Markdown、GitHub Issueなどを別途設計する必要がある。
- 実行回数、時間、モデル使用量、同一失敗回数を機械的に監視する専用の
  オーケストレーターは設定されていない。
- この調査メモ用リポジトリには、アプリケーションの自動テストやCIがないため、
  Markdown調査の合否は書式診断、リンク、差分、人またはエージェントによる
  内容確認が中心になる。

現在の環境で最初に導入するなら、外部サービスや新しいCLIを増やす前に、
対象のコーディングリポジトリへ次を用意するのが現実的である。

1. `AGENTS.md`に、1ループで扱う作業単位、変更禁止範囲、正しい検証コマンドを書く。
2. 要件を機械判定できるチェック項目へ分解し、Git管理のJSONまたはIssueへ保存する。
3. Copilot Agent HostをAutopilotで実行し、毎回一項目だけ実装させる。
4. 既存のテスト、ビルド、lint、型チェックを完了条件にする。
5. 最大反復回数と、同じ失敗が続いた場合の停止条件を依頼文に明記する。
6. 最後のマージ、デプロイ、削除は人の承認を残す。

この段階なら、追加導入なしで現在の機能を生かせる。PCを閉じても定期的に動く
ループが必要になった時点で、GitHub ActionsとGitHub Agentic Workflows、
または別のスケジューラーを追加する。GitHub Agentic WorkflowsをCLIから管理する
場合は、現在未導入のGitHub CLIが追加で必要になる。
