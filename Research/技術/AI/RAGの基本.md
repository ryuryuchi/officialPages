# RAGの基本

## 概要

生成AIの話で使われるRAG（Retrieval-Augmented Generation、検索拡張生成）が何を指す言葉なのかを、言語・フレームワーク・データベースとの違いも含めて初心者向けに整理する。

## 結論

RAGは**プログラミング言語でも、単独のフレームワークでもない**。質問に関係する資料を先に検索し、その検索結果をLLM（大規模言語モデル）へ渡して回答を生成させる、アプリケーションの構成方法・設計パターンである。

一言で言えば、RAGは「LLMに、回答前に関連資料を読ませる仕組み」である。モデルの再学習をしなくても、社内文書、製品マニュアル、最新情報などを回答の根拠に使える。ただし、検索結果が間違っていたり不足していたりすれば、RAGでも正しい回答は保証されない。

## 詳細

### RAGは何ではないか

| 用語 | RAGとの関係 |
| --- | --- |
| プログラミング言語 | RAG専用の言語はない。Python、TypeScript、Java、Goなどで実装できる |
| フレームワーク | RAGそのものはフレームワークではない。LangChainやLlamaIndexなどのフレームワークで構築しやすくできる |
| LLM | 回答を文章として生成する部品。RAGはLLMの前段に検索処理を追加する |
| ベクトルデータベース | 文書を検索するための保存先の一つ。RAGに使えるが、RAGそのものではない |
| ファインチューニング | モデルの重みを学習し直す方法。RAGは通常、モデルの重みを変更せず、質問時に資料を渡す |

### 基本の処理の流れ

```text
文書を集める
  ↓
文書を小さなまとまり（チャンク）に分ける
  ↓
各チャンクを検索しやすい表現（埋め込み）に変換して保存する
  ↓
ユーザーの質問を受ける
  ↓
質問に関係するチャンクを検索する
  ↓
質問と検索結果をLLMに渡す
  ↓
LLMが検索結果を参考に回答する
```

このうち、文書の分割・埋め込み・保存は事前に行うことが多い。質問のたびに行うのは、質問を検索し、関連する資料を取り出し、LLMへ渡して回答を生成する処理である。

### 身近な例

会社の就業規則PDFをLLMにそのまま覚えさせるのではなく、次のように使う。

1. 就業規則を数百〜数千文字程度のチャンクに分割する。
2. 各チャンクを検索用のベクトルに変換して、検索システムへ登録する。
3. 「有給休暇は何日ある？」という質問を受ける。
4. 質問と意味が近いチャンクを検索する。
5. 見つかった条文を質問と一緒にLLMへ渡す。
6. LLMが条文を根拠に回答する。

この場合、就業規則をモデルに再学習させているわけではない。質問時に必要な部分だけを一時的な文脈として渡している。

### 使われる部品

- **LLM**: 検索結果を読み、自然な文章にまとめる。例としてGPT、Claude、Geminiなどがある。
- **埋め込みモデル**: 文書や質問を、意味を反映した数値ベクトルへ変換する。
- **検索システム**: ベクトル検索、キーワード検索、または両者を組み合わせたハイブリッド検索を行う。
- **データストア**: ベクトルデータベース、検索エンジン、通常のデータベースなど。保存するデータや規模に応じて選ぶ。
- **オーケストレーションコード**: 検索、権限確認、プロンプト作成、LLM呼び出し、引用表示などをつなぐアプリケーションコード。

### フレームワークとの関係

LangChainやLlamaIndexは、RAGでよく必要になる文書読み込み、分割、検索、LLM呼び出しなどを組み合わせやすくするライブラリ／フレームワークである。これらを使わず、各サービスのAPIを直接呼び出してRAGを実装することもできる。

したがって、次の整理が分かりやすい。

```text
RAG              = 仕組み・設計パターン
LangChain等      = その仕組みを組み立てるための道具
Python等         = 道具を使って実装するプログラミング言語
LLM              = 最終的な文章を生成するモデル
```

### RAGとファインチューニングの違い

| 観点 | RAG | ファインチューニング |
| --- | --- | --- |
| 情報の追加 | 検索結果を質問時に渡す | 学習データでモデルの重みを更新する |
| 最新情報への反映 | 文書を更新して再登録しやすい | 再学習が必要になりやすい |
| 根拠の提示 | 検索元の文書やURLを表示しやすい | 回答の根拠を直接取り出せるとは限らない |
| 主な用途 | 社内文書検索、FAQ、規程・マニュアル回答 | 口調・形式・特定タスクの学習 |
| 注意点 | 検索品質と渡す文脈に強く依存する | 学習データの品質、コスト、再学習管理が必要 |

実際のシステムでは、RAGとファインチューニングを併用することもある。

### RAGの利点と限界

**利点**

- モデルの学習後に追加された資料を利用しやすい。
- 非公開の社内資料を、モデル全体の再学習なしで参照させられる。
- 検索した資料や引用元を回答に添えやすい。
- モデルが持つ知識と外部資料を組み合わせられる。

**限界**

- 検索が関係ない資料を返すと、回答も誤る可能性がある。
- 資料の分割方法、検索条件、取得件数、プロンプトの設計で品質が変わる。
- 資料に答えがない場合でも、LLMが推測してしまうことがある。
- 権限管理を別途設計しないと、ユーザーが見てはいけない文書を検索結果に含める危険がある。
- 文書の更新、重複除去、評価、監視などの運用が必要である。

そのため、「RAGを導入すればハルシネーションがなくなる」という理解は正しくない。RAGは回答を根拠資料へ近づける手段であり、検索・生成・権限・評価を含むシステム全体の品質管理が必要である。
