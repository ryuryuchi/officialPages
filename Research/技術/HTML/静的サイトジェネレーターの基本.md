# 静的サイトジェネレーターの基本

## 概要

静的サイトジェネレーター（Static Site Generator、SSG）が何をするものか、
通常のHTML手書き、サーバーでページを生成するWebアプリ、CMSとどう違うかを
初心者向けに整理する。また、SSGを自作できる範囲と、最初に試す方法を確認する。

## 結論

静的サイトジェネレーターは、Markdownやデータファイル、テンプレートから、
公開前に完成済みのHTMLファイルをまとめて生成するツールである。利用者が
ページを開くたびにHTMLを作るのではなく、あらかじめ作ったHTML、CSS、
JavaScript、画像などをWebサーバーやCDNが配信する。

典型的な流れは次のとおりである。

```text
記事・データ + レイアウト・テンプレート
                    |
                  build
                    v
       HTML / CSS / JavaScript / 画像
                    |
             公開先へ配置・配信
```

したがって、SSGが特に得意なのはブログ、技術文書、会社紹介、ポートフォリオ、
製品紹介、変更頻度が極端に高くないサイトである。生成後のファイルは
GitHub Pagesなどの静的ホスティングへ配置でき、常時動くアプリケーション
サーバーやデータベースを必須としない。

自作も可能である。最小構成なら、入力ファイルを読み、共通レイアウトへ
差し込み、出力先へHTMLを書き出すだけで成立する。ただし、Markdownの解釈、
テンプレート、URL設計、一覧・タグ・サイトマップ、リンク検査、画像処理、
差分ビルド、開発用サーバーなどを追加すると、既存のSSGを使う価値が大きくなる。

## 詳細

### 「静的」とは何か

ここでいう静的とは、ページのHTMLをリクエストごとにサーバー側で作らず、
ビルド時に作ったファイルをそのまま返すという意味である。JavaScriptを
含められないという意味ではない。生成されたページにJavaScriptを含めて、
ブラウザーからAPIを呼ぶ、検索を動かす、フォームサービスを使う、といった
動作を追加することはできる。

一方、ログイン中の利用者ごとの表示、現在の在庫、個人別の請求情報などを
毎回変えるページは、SSGだけでは扱いにくい。クライアント側のJavaScript、
外部API、サーバーサイドレンダリング（SSR）などを組み合わせるか、動的な
Webアプリケーションとして作る。

### SSGが実際に行う処理

SSGは製品ごとに機能が異なるが、概ね次の処理を担当する。

1. Markdown、HTML、JSON、YAMLなどの入力ファイルを読み込む。
2. タイトル、日付、カテゴリ、URL用の識別子などのメタデータを読む。
3. 本文をHTMLへ変換する。
4. ヘッダー、フッター、サイドバー、記事レイアウトなどのテンプレートを
   適用する。
5. 記事一覧、カテゴリ一覧、前後の記事リンクなどを生成する。
6. CSS、JavaScript、画像などの静的ファイルをコピーまたは最適化する。
7. `dist`、`public`、`_site`などの出力フォルダーへ完成ファイルを書き出す。
8. ローカル開発サーバーで確認し、出力フォルダーをホスティングへ配置する。

Eleventyの公式チュートリアルでは、MarkdownとHTMLのテンプレートから
`_site`へ`index.html`などを生成し、`--serve`でローカル確認を行う。
Hugoでは、コンテンツを`content`へ置き、ビルド成果物を`public`へ出力する。
出力先の名前はツールごとに異なるが、考え方は同じである。

### 手書きHTMLとの違い

ページが少ないうちは、HTMLを直接書く方が簡単である。しかしページ数が
増えると、全ページへ同じヘッダーやフッターを貼り付けることになり、
デザイン変更時の修正漏れが起こりやすい。

SSGでは、記事本文と共通レイアウトを分ける。例えばタイトル部分だけを
Markdownで書き、HTMLの骨組みやナビゲーションはテンプレートに置く。
テンプレートを1か所直して再ビルドすれば、全ページへ反映できる。

### CMSや動的Webアプリとの違い

| 方式 | ページを作るタイミング | 得意なもの | 注意点 |
| --- | --- | --- | --- |
| 手書きHTML | 人がファイルを直接作成 | 小規模な固定ページ | 共通部分の重複が増える |
| SSG | 公開前のビルド時 | ブログ、文書、紹介サイト | 更新後に再ビルドが必要 |
| CMS | 管理画面への投稿時またはアクセス時 | 複数人での編集、投稿管理 | 運用、更新、セキュリティが必要 |
| SSRなどの動的アプリ | 多くはアクセス時 | ログイン、個人別表示、リアルタイム情報 | サーバーや実行環境が必要 |

SSGとCMSは排他的ではない。ヘッドレスCMSやAPIからビルド時にデータを
取得してSSGする構成もある。また、Astroのように、基本は静的生成にしつつ、
必要なページだけリクエスト時に生成する構成も選べる。

### 自作できる最小構成

「SSGそのものを理解する」目的なら、次のような小さな構成を自作できる。

```text
my-generator/
├─ content/
│  ├─ index.txt
│  └─ about.txt
├─ templates/
│  └─ page.html
└─ build.py
```

`build.py`で行う処理は、最初は次の程度でよい。

1. `content`内のファイルを列挙する。
2. 本文を読み込む。
3. `{{ title }}`や`{{ content }}`のような置換文字列へ値を入れる。
4. ファイル名をURLに対応する出力先へ変換する。
5. `dist`へHTMLを書き出す。

この段階ならPythonの`pathlib`と文字列処理だけでも作れる。Markdownも扱う
場合は、Markdownパーサーを利用するか、最初は入力をHTMLとして割り切ると
実装量を抑えられる。入力をHTMLとして扱う場合でも、外部から受け取った
信頼できない文字列をそのままHTMLへ埋め込まないなど、エスケープの設計は
必要である。

ただし、実用的なSSGにするには、次の機能が必要になる。

- Markdownの見出し、リンク、コードブロック、画像などの変換
- YAMLなどのフロントマターの解析と入力値の検証
- HTMLエスケープ、URLの正規化、パス区切りの扱い
- 共通レイアウト、部品、テンプレートの継承
- 記事一覧、タグ、カテゴリ、ページネーションの生成
- 下書き、公開日、更新日、タイムゾーンの扱い
- 画像・CSS・JavaScriptのコピーと最適化
- 変更監視、ローカルサーバー、エラーの行番号表示
- 壊れたリンク、重複URL、未設定メタデータの検査

そのため、学習では小さく自作し、実際のサイト公開ではEleventy、Hugo、
Astroなどを使う、という使い分けが現実的である。

### 初心者が試すなら

目的別には次の選び方が分かりやすい。

- HTMLとMarkdownの変換を理解したい: Eleventy
- 大量の文書を高速に生成したい: Hugo
- コンポーネントやJavaScriptとの組み合わせも学びたい: Astro
- まず仕組みだけ確認したい: Pythonで「本文をテンプレートへ差し込む」最小版

最初の練習では、トップページ1枚と記事2枚を作り、次の変化を確認すると
SSGの役割がつかみやすい。

1. 記事をMarkdownで追加する。
2. 同じレイアウトから記事ページを複数生成する。
3. テンプレートのフッターを1か所変更する。
4. 再ビルドして全ページへ変更が反映されることを確認する。
5. 出力フォルダーだけを静的ホスティングへ公開する。

### 何を選べばよいか

次のような場合はSSGが向いている。

- 内容をGitで管理したい。
- ページの大部分が誰に対しても同じである。
- 表示速度、キャッシュ、運用の単純さを重視する。
- GitHub Pagesなど、静的ファイルを置くだけの公開先を使いたい。

反対に、管理画面から頻繁に投稿する編集者が多い、利用者ごとに内容が
異なる、アクセス時点のデータが重要、といった場合は、CMSや動的処理を
組み合わせる方が適している。
