# APIの基本

## 概要

APIとは何か、アプリ同士がどのように情報をやり取りするのかを、初めて学ぶ人向けに整理する。
特に、Webサービスでよく使われるHTTP APIの基本用語、利用の流れ、注意点を説明する。

## 結論

API（Application Programming Interface）は、ソフトウェアが別のソフトウェアの機能やデータを利用するための「決められた窓口」である。

たとえば、飲食店では客がメニューから料理を注文し、店員が厨房へ伝え、完成した料理を客へ運ぶ。APIに置き換えると、客側のアプリが**クライアント**、厨房側のシステムが**サーバー**、注文を受け渡す仕組みが**API**に近い。

利用者はサーバー内部の作り方を知らなくても、APIの仕様に従ってリクエスト（要求）を送れば、レスポンス（応答）を受け取れる。ただし、利用前には必ず公式ドキュメントでURL、送信方法、認証、料金、回数制限を確認する必要がある。

## 詳細

### APIでできること

APIを使うと、あるサービスの機能やデータを別のプログラムから利用できる。代表例は次のとおり。

- 天気サービスから現在の天気を取得する
- 地図サービスに住所を渡して地図を表示する
- 決済サービスへ支払い処理を依頼する
- GitHubからリポジトリやIssueの情報を取得する

APIはWeb専用の言葉ではない。OSやプログラミング言語のライブラリにもAPIがある。ただし、インターネット経由で使うAPIは「Web API」と呼ばれることが多い。

### 画面操作との違い

人は通常、Webサイトのボタンや入力欄などの画面（UI）を操作する。一方、プログラムはAPIへ決められた形式で直接要求を送る。

| 比較項目 | UI | API |
| --- | --- | --- |
| 主な利用者 | 人 | プログラム |
| 操作方法 | ボタン、画面、フォーム | URL、HTTPメソッド、データ |
| 応答 | 人が読む画面 | プログラムが処理しやすいデータ |

### 基本的な通信の流れ

Web APIでは、一般に次の順番で通信する。

1. クライアントがAPIのURL（エンドポイント）へリクエストを送る。
2. サーバーが認証情報や入力内容を確認する。
3. サーバーが検索、登録、計算などの処理を行う。
4. サーバーが処理結果をレスポンスとして返す。
5. クライアントが結果を画面表示や次の処理に使う。

「エンドポイント」は、APIの特定の機能を呼び出すURLである。たとえば、GitHub REST APIで特定の公開リポジトリを取得するエンドポイントは、次のような形になる。

```text
https://api.github.com/repos/OWNER/REPOSITORY
```

### リクエストを構成する主な要素

- **URL（エンドポイント）**: どの機能やデータを使うかを示す
- **HTTPメソッド**: 何をしたいかを示す
- **ヘッダー**: データ形式や認証情報などの付加情報を渡す
- **パラメーター**: 検索条件や対象IDなどを渡す
- **ボディ**: 登録・更新したいデータなどを渡す

よく使うHTTPメソッドは次のとおり。ただし、実際の動作はAPIの仕様で決まるため、名前だけで判断せずドキュメントを確認する。

| HTTPメソッド | 一般的な用途 |
| --- | --- |
| `GET` | データを取得する |
| `POST` | 新しいデータを作成する、処理を依頼する |
| `PUT` / `PATCH` | 既存データを更新する |
| `DELETE` | データを削除する |

### レスポンスを構成する主な要素

サーバーからのレスポンスには、主に次の情報が含まれる。

- **ステータスコード**: 成功または失敗の種類を示す3桁の番号
- **ヘッダー**: データ形式やキャッシュなどの付加情報
- **ボディ**: 取得したデータやエラーの詳細

代表的なHTTPステータスコードは次のとおり。

| コード | 主な意味 |
| --- | --- |
| `200 OK` | リクエストが成功した |
| `201 Created` | 新しいデータの作成に成功した |
| `400 Bad Request` | 入力やリクエストの形式に問題がある |
| `401 Unauthorized` | 有効な認証情報がない、または認証に失敗した |
| `403 Forbidden` | 認証済みでも操作する権限がない |
| `404 Not Found` | 対象のURLやデータが見つからない |
| `429 Too Many Requests` | 利用回数の上限を超えた |
| `500 Internal Server Error` | サーバー内部で問題が発生した |

### JSONとは

Web APIのデータ形式にはJSONがよく使われる。JSONは、名前と値の組み合わせをテキストで表せる形式である。

```json
{
  "name": "sample",
  "public": true,
  "stars": 10
}
```

この例では、`name`、`public`、`stars`が項目名であり、それぞれに文字列、真偽値、数値が入っている。APIによって項目名や入れ子構造が異なるため、レスポンス例や仕様書を確認してプログラムから必要な値を取り出す。

### REST APIとは

REST APIはWeb APIの代表的な設計方式の一つで、HTTPの仕組みを利用してリソース（ユーザー、商品、投稿など）を操作する。一般にURLで対象を表し、HTTPメソッドで取得・作成・更新・削除などの操作を表す。

すべてのWeb APIがREST APIというわけではない。SOAP、RPC、GraphQL、WebSocketなど、目的や通信方法が異なる方式もある。初心者はまずHTTP、JSON、リクエスト、レスポンスを理解すると、REST APIを学びやすい。

APIの仕様を機械可読に共有する標準としてOpenAPIがある。2026年8月31日時点の最新仕様は3.2.0で、HTTP APIの操作、入力、応答などをJSONまたはYAMLで記述できる。OpenAPIはAPIそのものの通信方式ではなく、API記述の仕様である。

### 認証とAPIキー

APIには誰でも利用できるものと、認証が必要なものがある。よく使われる認証情報にはAPIキーやアクセストークンがある。

APIキーやトークンはパスワードと同様に扱い、次の点を守る。

- ソースコードへ直接書き込まない
- GitHubなどの公開リポジトリへ登録しない
- チャット、画像、ログへ不用意に載せない
- 環境変数やサービスのシークレット管理機能を使う
- 漏えいした可能性があれば、無効化して再発行する
- 必要最小限の権限と有効期限を設定する

ブラウザーで動くJavaScriptへ秘密のAPIキーを埋め込むと、利用者からキーを確認できてしまう。秘密情報が必要なAPIは、原則として自分のサーバーを経由して呼び出す。

### 初心者向けの試し方

公開情報を取得する`GET` APIは、比較的安全に試しやすい。PowerShellでは、次の例でGitHubの公開リポジトリ情報を取得できる。

```powershell
Invoke-RestMethod `
  -Uri "https://api.github.com/repos/microsoft/vscode" `
  -Headers @{
    "Accept" = "application/vnd.github+json"
    "X-GitHub-Api-Version" = "2026-03-10"
    "User-Agent" = "api-learning-sample"
  }
```

結果にはリポジトリ名、説明、スター数などが含まれる。この例は公開情報の取得なので認証なしでも試せるが、認証しないリクエストにも回数制限がある。GitHub REST APIは日付ベースでバージョン管理され、現在は`2026-03-10`と`2022-11-28`がサポート対象である。ヘッダーを省略すると既定版になるため、再現性が必要な統合では対応版を明示する。

学習時は次の順番で確認するとよい。

1. 公式ドキュメントで対象のエンドポイントを探す。
2. 必要なHTTPメソッド、パラメーター、認証を確認する。
3. ブラウザー、PowerShell、`curl`、Postmanなどでリクエストを試す。
4. ステータスコードとレスポンスのJSONを確認する。
5. 動作を確認してから、自分のプログラムへ組み込む。

データの作成・更新・削除を行うAPIは実データを変更する。練習環境やテスト用アカウントが提供されている場合は、そちらを使う。

### APIを使う前の確認項目

- 公式ドキュメントと利用規約
- エンドポイントとHTTPメソッド
- 必須・任意のパラメーター
- 認証方法と必要な権限
- 無料・有料の範囲
- 単位時間あたりの利用回数制限（レート制限）
- エラー時のステータスコードとレスポンス
- APIのバージョンと廃止予定
- 取得したデータの保存・再配布が許可されるか
