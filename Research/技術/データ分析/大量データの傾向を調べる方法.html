大量データの傾向を調べる方法

概要

行数の多い表形式データから、全体の傾向、グループごとの差、時系列変化、 外れ値などを調べる方法を整理する。ローカルPCで始める場合を中心に、 データがメモリへ収まらない場合や、さらに規模が大きくなった場合の選択肢も扱う。

結論

  • 最初に行うのは、機械学習ではなく探索的データ分析（EDA）である。

件数、欠損率、分布、中央値・分位点、グループ別集計、時系列推移を確認する。

  • ローカルPCでCSVやParquetを分析するなら、まず

DuckDBで必要な列・行だけを読み、集計結果をpandasやグラフへ渡す方法が扱いやすい。 全データを最初からpandasへ読み込む必要はない。ただし、DuckDBもすべての処理を 必ずメモリ外で完了できるわけではない。

  • データは可能ならCSVからParquetへ変換する。Parquetは列指向形式なので、

必要な列だけを読む分析や圧縮に向いている。

  • グラフへ数百万行をそのまま描かない。全件で集計した結果を描くか、

目的に合った無作為抽出・層化抽出を使う。

  • 重要なのはデータ量そのものより、目的、PCのメモリ、処理内容、更新頻度である。

単一PCで足りなければPolarsのストリーミング、複数台での分散処理が必要なら Sparkやクラウドのデータウェアハウスを検討する。

詳細

「傾向」を具体的な問いにする

分析前に、何を傾向と呼ぶかを決める。問いが曖昧なままでは、目立つグラフを 偶然見つけただけになりやすい。

知りたいこと 主な方法 代表的な出力
全体像 記述統計、度数分布 件数、欠損率、平均、中央値、分位点
グループ差 グループ別集計、クロス集計 地域別・商品別の件数、率、中央値
時間変化 時系列集計、移動平均、前年同期比 日次・週次・月次の折れ線
値の偏り ヒストグラム、箱ひげ図 山の数、裾の長さ、外れ値
2変数の関係 散布図、相関、ビニング 相関係数、区間別平均
継続や離脱 コホート分析、ファネル分析 開始月別の継続率、段階別到達率
普段と違う動き ルール、分位点、異常検知 急増・急減した期間や対象

割合を見る場合は、分子だけでなく分母も保存する。例えば購入数が増えていても、 訪問者数がそれ以上に増えていれば購入率は下がっている可能性がある。

基本的な進め方

  1. 分析単位を決める
  • 1行が利用者、注文、アクセス、センサー測定のどれなのかを確認する。
  • 対象期間、タイムゾーン、重複の定義、集計の分母を決める。
  1. 品質を確認する
  • 行数、列型、欠損率、重複率、最小値・最大値、カテゴリ数を調べる。
  • 日付の範囲外、負にならない値の負数、単位違いなどを検査する。
  1. 全体の分布を確認する
  • 平均だけでなく中央値、四分位点、上位・下位の分位点も見る。
  • 外れ値を無条件に削除せず、入力ミスか実際の事象かを切り分ける。
  1. 切り口を変えて集計する
  • 時間、地域、商品、利用者属性などでグループ分けする。
  • 件数の少ないグループは偶然の振れが大きいので、件数も併記する。
  1. 可視化して仮説を作る
  • 時系列は折れ線、分布はヒストグラムや箱ひげ図、2変数は散布図を使う。
  • データ点が多い散布図は、透過、ビニング、hexbin、密度図を使う。
  1. 別の切り口と元データで検証する
  • 集計期間を変えて同じ傾向が残るかを確認する。
  • サンプルで発見した傾向は、最後に全件集計で確認する。

NISTの説明でも、EDAはグラフィカルな手法を中心に、生データ、単純な統計量、 複数の図を組み合わせて構造や予想外の特徴を探るものとされている。

データ量別の選び方

次の境界は固定的な行数ではない。列数、文字列の多さ、結合や並べ替えの有無、 PCのメモリによって必要資源が大きく変わる。

状況 向く方法 判断の目安
メモリへ余裕を持って収まる pandas + JupyterLab 対話的に加工・可視化したい
単一PCだがメモリへ収まらない DuckDB、Polars Lazy/Streaming CSV・Parquetを直接集計したい
DBにすでに保存されている SQLで先に絞り込み・集計 生データをPCへ全件転送しない
複数台が必要、定期的に大規模処理 Spark、データウェアハウス 分散処理、共同利用、運用管理が必要

pandasはインメモリ分析を前提としており、メモリより大きいデータは扱いにくい。 公式資料では、必要列だけの読み込み、効率的な型、チャンク処理が案内されている。 ただし、複雑なgroupbyのようにチャンク間の調整が必要な処理は難しいため、 その場合はDuckDBやPolarsなどに任せる方がよい。

PolarsのLazy APIは、述語・射影プッシュダウンなどの最適化を行える。ストリーミング 実行はクエリをバッチに分け、メモリへ収まらないデータを処理できる。ただし、すべての 演算がストリーミング対応ではなく、非対応の演算はインメモリエンジンへ切り替わる。 explainや物理プランのグラフで、実行計画とメモリ負荷を事前確認する。

Spark SQLは構造化データを分散処理する仕組みで、SQLとDataFrame APIを使える。 ただし、環境構築と運用の負担が増えるため、ローカルで終わる分析へ最初から 導入する必要はない。

ローカルPCでの実用的な構成

既存のPythonのuvの基本に沿って、次の構成から始められる。

uv init data-trend-analysis
Set-Location data-trend-analysis
uv add duckdb pandas matplotlib jupyterlab
uv run jupyter lab

DuckDBはParquetをテーブルへ全件取り込まずに直接SQLで読める。次の例では、 全件から月・カテゴリ別の集計を行い、小さくなった結果だけをpandasへ渡す。

import duckdb

summary = duckdb.sql(
    """
    SELECT
        date_trunc('month', event_time) AS month,
        category,
        count(*) AS record_count,
        avg(value) AS mean_value,
        median(value) AS median_value,
        quantile_cont(value, 0.25) AS p25,
        quantile_cont(value, 0.75) AS p75
    FROM read_parquet('data/*.parquet')
    WHERE event_time IS NOT NULL
    GROUP BY 1, 2
    ORDER BY 1, 2
    """
).df()

ax = summary.pivot(
    index="month",
    columns="category",
    values="median_value",
).plot()
ax.set_ylabel("median value")

CSVしかない場合もreadcsvauto('data/*.csv')で同様に読める。繰り返し分析するなら、 型を確認してParquetへ変換しておくと、必要列だけの読み込みと圧縮を利用しやすい。

DuckDBはメモリを超える処理でディスクへ退避できるが、複数のブロッキング演算、 一部の集約、PIVOTなどではメモリ不足が起こり得る。データ量だけで安全と判断せず、 十分な空きディスク、memory_limit、一時ディレクトリ容量を監視し、本番相当データで 試験する。

大量データを扱う工夫

  • 必要な列と行だけ読む: SELECT *を避け、期間や対象を早い段階で絞る。
  • 先に集計する: 全件をPythonへ渡さず、SQLで日次・カテゴリ別などへまとめる。
  • 列指向形式を使う: 分析用途ではCSVよりParquetを優先する。
  • 段階的に調べる: 小さなサンプルでコードを作り、集計結果を確認してから全件で実行する。
  • 再現可能にする: サンプリングの乱数シード、抽出条件、SQL、データ期間を記録する。
  • 母集団と不確実性を残す: サンプル件数、抽出確率、信頼区間を併記し、小標本の差を

確定的に扱わない。

  • 中間結果を保存する: 重い集計はParquetやテーブルへ保存し、グラフ調整のたびに

全件を再計算しない。

  • 実行計画を確認する: 不要な全件ソート、大きな結合、列の読み過ぎを見つける。

サンプリングの使い分け

全件集計が可能でも、可視化や試行錯誤ではサンプルが役立つ。

方法 向く場面 注意点
単純無作為抽出 全体を代表する概観 少数グループがほぼ消えることがある
層化抽出 地域・カテゴリごとに比較 元の構成比と異なる場合は重み付けが必要
系統抽出 並びに周期性がないデータ 周期と抽出間隔が一致すると偏る
時間窓抽出 特定期間の詳細調査 季節性やイベントの影響を全体傾向と誤認しやすい

先頭から一定件数を取る方法は無作為抽出ではない。データが時刻、地域、ファイル順で 並んでいると強く偏る可能性がある。希少な事象を探す場合は、通常データと希少データを 分けて抽出し、最終的な発生率は全件の分母で計算する。

読み違いを防ぐ注意点

  • 相関は因果関係ではない: 同時に動く第三の要因がある可能性を残す。
  • 平均だけを見ない: 歪んだ分布では中央値や分位点も併記する。
  • 季節性を除かないまま比較しない: 曜日、月、祝日、キャンペーンの影響を確認する。
  • 集計単位を変えて確認する: 全体とグループ別で結論が逆転する

シンプソンのパラドックスに注意する。

  • 欠損をゼロ扱いしない: 未観測、不明、該当なしを区別する。
  • 何度も探索した結果を確定的に扱わない: 多数の切り口を試すほど、

偶然それらしい差を見つけやすい。重要な仮説は別期間や別データで再検証する。

  • データ収集の偏りを確認する: 観測された利用者だけから、離脱者や未利用者を含む

全体の傾向を断定しない。

最初に作るとよい出力

最初の分析では、次を1つのノートブックまたはレポートに揃えると全体像を掴みやすい。

  1. データ期間、総行数、分析単位
  2. 列名、型、欠損率、ユニーク数
  3. 数値列の中央値、四分位点、最小値、最大値
  4. 主要カテゴリ別の件数と割合
  5. 日次または月次の件数・主要指標
  6. 主要指標のヒストグラムと箱ひげ図
  7. 気付いた点、未確認事項、次に検証する仮説
